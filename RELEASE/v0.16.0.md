# RELEASE v0.16.0: LLM traces, metric-level views (steps L3 and L6 alerts)

**Status:** ready
**Design choices (ARCH 06):** D3
**Exit gate:** the LLM page answers calls, tokens, cost, error rate and p50/p95/p99 by model, tool and span kind with numbers equal to those computed from the batch that was sent; sessions open turn by turn; an alert fires on cost, tokens or error rate per model
**Depends on:** 0.15
**Requirements:** R-AI5 R-AI6 R-AI10

Why one release: all of it aggregates many spans over a window (analytics, sessions, users, alerts), sharing the same bounded JSON-path statements in `src/query/llm.rs`; the alert condition runs the analytics statement.

## Scope

Step L3, LLM analytics and sessions (ARCH 08 sections 6.4 and 6.5):

- `GET /orgs/{org}/llm/overview`, `/llm/breakdown?by=model|provider|kind|tool`, `/llm/sessions`, `/llm/sessions/{id}`, `/llm/users`
- Statements read raw spans of a JSON-layout table within the window cap; every attribute name is a bound JSON path; token and cost sums count model-call spans only; cost is reported plus price-table estimate (0.15 prices), shown apart; sessions group by `session.id` or `gen_ai.conversation.id`
- UI: an LLM page (totals, series, by model, tools, kinds, sessions with turn-by-turn view, users); results honour the redaction layer from 0.15

Step L6b, alerts on LLM metrics:

- A rule query kind `llm` (metric `cost`, `tokens`, `calls`, `error_rate`, `latency_p95`; optional model; per model or in total; threshold on the look-back window) evaluated by the existing engine, lease, history and notifications; preview is a GET and writes nothing

## Notes

ADR 0017 records: analytics on JSON tables only (flat tables are refused, not guessed); sums count model-call spans only so parent spans that roll tokens up are not double counted; raw spans with no rollup (windows stay under the 31-day cap); the alert condition reuses the analytics statement.

Limits to carry into the notes: no rollup planner for long ranges; Services RED still counts only server and consumer spans; percentiles are approximate (`approx_percentile_cont`).

## Built

See ADR 0017. Verified live on GreptimeDB v1.3.0: a generated OpenInference batch is sent to a real trace v2 table and every number is compared with the one computed from the batch: calls, errors, prompt and completion tokens and reported cost per model, provider, span kind and tool (with the model filter and the filter bar), the overview totals and series, sessions (traces, spans, model calls, tokens), a session's turns in order with each root input and output, users (traces, sessions, calls), a cost rule that fires over half the spend and not over twice the spend, and an error-rate rule per model that fires exactly for the models that had a failing call, with the batch's rate. Offline: price estimate, flat-table refusal, window cap, bound paths in every statement, validation of the rule, preview that writes nothing, masked session snippets for viewers. Browser pass (admin): LLM page overview (80 calls, 24,488 prompt tokens, 7.5% error rate, by model), sessions with a session opened turn by turn, an LLM error-rate rule previewed in the alert editor (11.4%, 4.2%, 4.8% per model, the same as the page) (`images/ui_llm_overview.png`, `ui_llm_sessions.png`, `ui_alert_llm.png`).

Fixed on the way: a session's turn list returned the prompt snippets under keys the content rules did not match, so viewers would have read them; the keys are now `input.value` and `output.value` and a test covers it.

Limits: raw spans only (no rollup for long ranges); flat tables refused; cost estimates only in the overview and the per-model breakdown (the others show reported cost); percentiles approximate; only spans that carry the session id or user id are counted in a session or user row; an anomaly rule cannot use an LLM metric yet; Services RED still counts server and consumer spans only; the masked view of the LLM page and the alert editor was not exercised in a browser as a viewer.

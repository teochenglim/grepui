## Notes

`TQL EVAL` takes no bound parameters for its expression, so the PromQL text is embedded in the statement; that is the one place request text reaches SQL, and it passes `query::metrics::check` first: one expression, no `;` or `#`, no control characters, no backslash outside a string, strings decoded (`\x`, `\u`, `\U`, octal) before looking for `__schema__` or `__database__`, which select another database in every spelling (verified live on v1.3.0: bare, quoted and case variants all crossed databases, so the check is case-insensitive and on decoded text). The start, end and step are integers we format; the step is raised to a floor of window/1000 seconds (at most 1000 points per series) and capped at a day; at most 100 000 rows are read. TQL stays refused in SQL mode.

`TQL EVAL` works through the MySQL prepared-statement protocol. Its result columns are named by the query (`ts`, `greptime_timestamp`, `prom_rate(...)`), so `to_series` tells the roles apart by type: text columns are labels, the all-integer numeric column is the time, the other numeric column is the value. A PromQL error from the database is reported as a generic 400 (the detail is logged, R-Q3). TQL runs in the connection's database, which is the default org's database today; per-org connections (v0.11.0) must pass the org's database explicitly.

Metric list: logical metric-engine tables of the org's database (`engine = 'metric'`, not the physical table), with counter or gauge read from the options GreptimeDB records for OTLP metrics; labels are the table's tag columns. OTLP names get a `_total` suffix for counters (`http_server_request_count` is the table `http_server_request_count_total`). Plain tables without the metric engine are reachable by SQL but not listed.

The share spec (`Spec`: chart, kind, stream, query, range) is percent-encoded in the URL and mirrored by the page; unknown keys or values fail instead of showing something else. A saved view may now be of kind `metrics` with the same keys (stored share links); the Views menu on the Metrics page is not built yet.

The playground now also seeds two demo metrics over OTLP (`http_server_request_count` counter with `http.status_class`, `process_cpu_utilization` gauge) per service, as pure functions of the timestamp so the live trickle continues the series and tests can assert exact values. Verified live: exact counter and gauge values at sample times, `rate` within 5% of the generator's slope, SQL on the metric table, names and labels. Checked in a browser: line chart with legend, SQL mode with a deep link. Not exercised in a browser: the bar and table charts, the Copy link button, truncation at the sample limit. Small cosmetic artifact: the demo's live trickle leaves tiny dips at the newest end of rate charts.

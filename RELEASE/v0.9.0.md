## Notes

Real-time here means short-interval polling of GreptimeDB (default 10 s, 5-60 s), not an ingest hook; ARCH 07 states the difference.

**What was built.** Rules (`scheduled`, `realtime`, `composite`, `anomaly`) with SQL, PromQL or builder queries; interval or five-field UTC cron; look-back; cooldown; compare-with-past (ratio or difference); dedup by fingerprint of chosen label values; downtimes; webhook and SMTP destinations with `{{variables}}` templates and test-send; incidents with a timeline; history of every evaluation (30 days); JSON import and export; a lease per rule (ADR 0010); a preview that runs a rule once and writes nothing. UI: Alerts (rules, history, incidents, destinations, downtimes) and the editor. Routes: `/alerts`, `/destinations`, `/downtimes`, `/incidents`. Schema version 4 (`grepui_alert_items`, `grepui_alert_history`), so an existing store needs `grepui migrate`. New flags: `--no-alerts`, `--smtp`, `--smtp-from`. The playground seeds one demo rule over the demo error logs. No new dependency (cron, SMTP and the HTTP POST are written in the crate).

**Limits, stated.** Webhooks are `http://` only and SMTP is plain with no login (grepui has no TLS client): use a relay. The lease is write-then-read, not compare-and-set, so a duplicate evaluation is possible in a race and the dedup window absorbs it. A real-time rule pauses six intervals after a run over its budget. A rule's SQL must return the value as its last numeric column (other columns become labels); an anomaly query returns a time column first. No resolved notifications and no repeat reminders while a rule stays firing beyond cooldown/dedup. Owner is `local` until v0.11.0. Not exercised in a browser: creating a rule from the form (editing, preview and history of the seeded rule were), the builder and composite forms, downtimes and import tabs, deleting. Live: exact counts per service and builder count against the seeded batch, lease handover on GreptimeDB v1.3.0, and the real error-path fix (a rule over `service_name` on the logs table errored on the real database; the logs table keeps the service in `resource_attributes`).

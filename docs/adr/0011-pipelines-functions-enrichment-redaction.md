# 0011 Pipelines, functions, enrichment and redaction

Status: Accepted (v0.10.0).

## Context

Four features touch places grepui has been careful about: GreptimeDB's server-wide pipeline API, user text that becomes SQL, new tables in the org's telemetry database, and the shape of every response.

## Decision

- **Pipelines are namespaced per org and written only by admins.** GreptimeDB pipelines are server-wide, so grepui stores an org's pipeline as `<org>.<name>` (name `[a-z0-9_]`), lists only that prefix and refuses any other path (`pipelines::check_path` is the gate in front of the HTTP client). Create and delete need `--admin-writes` and are logged as `audit`; a dry-run changes nothing and is open. A version is deleted by the creation time GreptimeDB gives it, and "delete" removes every version. The HTTP address is `--pipeline-http` (default `--greptime-http-public`). The small HTTP client moved out of the playground (`src/http.rs`), still without TLS.
- **Functions are text macros whose arguments are bound.** `@name(1, 'x')` in SQL mode and dashboard SQL panels is replaced by the saved body, whose `$1`, `$2` become `?`; the arguments are literals (numbers, quoted text, booleans) parsed by a small scanner and sent as binds, and in a panel they are merged with the variable binds in text order. A body cannot contain `@`, so recursion cannot exist; it also has no `?`, `;` or comments. The expanded statement passes `sqlmode::check` like any SQL, which is the real boundary. Alert rules do not expand functions and refuse the syntax.
- **Enrichment tables go through the admin gate as generated statements.** `enrich_<name>` in the org's database, columns from a validated header (never rewritten), types inferred from all rows (leading zeros stay text), at most 5 000 rows, 30 columns and 1 MB (the upload route alone raises the 64 KB body limit). The three statement kinds (create, chunked insert, drop) are produced by `enrich::Spec` and `admin::check` accepts one only if parsing it back and regenerating gives the same text, for an `enrich_*` table of the org's database. Uploaded cells are bound values and never written to the audit log. With key columns rows upsert at one time-index value; without, every row is kept.
- **Redaction is one response layer, with rules mirrored in memory.** Rules (field, mask `full`/`partial`/`hash`, exempt roles) live in the state store; `api::redaction::layer` masks the `data` of every JSON response and the body of every CSV or NDJSON export under `/api/v1/orgs/`, so a new handler cannot forget it. The layer is a `route_layer`: it reads the matched route template (never the raw path, which can be spelled with percent escapes) to exclude only the two rule routes and to recognise public links, and it resolves the org from the decoded path segment through the same `Orgs::resolve` as the handlers; if that fails it withholds the response. A rule matches a key equal to the field or ending in `.field` (any case, any depth, also JSON inside string cells) and a CSV header. Rules are held in memory and refreshed every 5 s (and at once on the replica that changed them), so no response waits on a read; until the first load after startup data responses answer 503 rather than leak, and an export line that cannot be parsed is replaced, not passed on. Roles until access control (v0.11.0): `admin` when `--admin-writes` is on, `viewer` otherwise and always on public dashboard links; changing rules needs the admin stand-in.

## Consequences

Redaction does not see a column renamed by a query (`SELECT password AS p`), a secret inside a free-form log body, or `meta.sql` (the query text, not data). Other replicas pick up a rule change within about 5 s. The small-config table `grepui_alert_items` now also holds `function` and `redaction` items (the name predates them; renaming needs a migration, so it stays). Enrichment is a data-plane write limited to tables named `enrich_*`, enabled only with `--admin-writes`. Cipher-key encryption of fields is not offered.

# 0014 Reports, RUM view and operate: result cache, metrics, shutdown, read-only check

Status: Accepted (v0.13.0).

## Context

v0.13.0 adds scheduled reports (R-E1), a RUM view over GrepRUM's tables (R-U1) and the operating pieces a long-running service needs: a result cache with single-flight (R-O1), `/metrics` (R-O2), graceful shutdown, pool limits and a read-only account check (R-O3).

## Decision

- **Reports** are kind `report` rows of `grepui_alert_items` (spec: name, `dashboard` or `view` target, `html` or `csv`, a five-field cron in UTC, hours of data, up to 20 recipients, enabled), with a `reportstate` row per report (last slot taken, last outcome and error, run count). A dashboard report runs every non-text panel with its stored query and default variables; a view report runs a saved logs view (search or SQL mode, through the same gates as the interactive routes). Reports are admin-only to create and read, because recipients can be anyone. A render is **masked by the org's redaction rules as a viewer** (the response layer never sees an in-process render); if the rules are not loaded yet the run fails instead of sending. HTML is one self-contained page with inline styles and every value escaped. The body is mailed through the alert sender (plain SMTP, `--smtp`); a body with a line over 900 characters (always for HTML) travels base64-encoded so no SMTP line passes 998.
- **Once per slot across replicas.** Every replica runs the scheduler. A report's next slot is the latest cron match since the last slot taken (a long outage gives one catch-up send, never one per missed slot). A replica takes the slot by a lease (write then read, as for alert rules, ADR 0010), re-reads the state, and **writes the slot before sending**: delivery is at most once per slot, and a failed send is recorded and not retried until the next slot (or "Send now"), so a mail outage cannot become a storm. Every run, scheduled or manual, writes a history row `report:<id>` (`scheduled_sent`, `scheduled_failed`, `manual_sent`, `manual_failed`) in `grepui_alert_history`; the alert history list leaves those out.
- **RUM** reads GrepRUM's `events` table in the org's database, with fixed statements and bound parameters (`query::rum`): overview, time series, top pages, INP percentiles and good / needs-improvement / poor shares (INP is the one vital GrepRUM collects; other `$web_vital` names are ignored), JavaScript errors grouped by message with a stack sample, and sessions derived from the events (GrepRUM's own `sessions` table is not needed). The table counts as GrepRUM's only if it has the columns the queries use; otherwise `/rum/status` says `installed: false` and lists what is missing, and the data routes answer 404 with an explanation. Nothing writes.
- **Result cache** (`cache::Cached`, between the API and the governed reader): reads made for a signed-in caller only, keyed by source, org, role, statement and typed binds (hashed); a TTL (`--cache-ttl-secs`, 5 on the command line, 0 and off for the library and tests); identical concurrent reads wait for one (single-flight, with a failure shared by the waiters and never cached, and a leader that goes away releases them with an error); bounded by an entry count and an estimated size, oldest first, and a result over an eighth of the size cap is not kept. Reads of `grepui_*` tables, the process list, health probes, and reads with no caller (the alert engine, reports) are never cached. The key carries the role, not the user, so people of one role in one org share results; the redaction layer still masks each response for its caller.
- **`/metrics`** is Prometheus text: build info, uptime, requests by route template and status (never the raw path), a database latency histogram (reads that reached the database), database errors, cache hits, misses, single-flight joins and evictions, and alert evaluations. It is for a platform admin, or a scraper with `--metrics-token` (a bearer token good for that one route).
- **Shutdown and pool.** `server::run` stops accepting on SIGTERM or Ctrl-C, lets running requests finish, and closes anyway after `--shutdown-grace-secs` (30). `--pool-max-connections` (8) sets each source's pool. `--read-only-user` makes startup try to create and drop a fixed probe table (`grepui_write_probe`) in the default org's database through the writer, and warn if it worked; the statements are constants and the database name is validated. It is opt-in because it is the one DDL outside migrations and admin templates.

## Consequences

The cache is per process and a TTL-old view is by design (5 s default); there is no per-request bypass yet. Reports are at most once per slot, not exactly once. The read-only check cannot tell a read-only account from one that lacks only CREATE rights, and grepui's own state writes need an account that can write to the metadata database, so the flag fits a data database that grepui's account may not write. Requests that match no route are not counted in `/metrics`. RUM covers INP only because GrepRUM collects only INP; session replay stays unsupported.
